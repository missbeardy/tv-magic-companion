# FieldBourne codebase review — 16-09-2026

Read-only review of the working tree at commit `6c65eba` (v1.1.194). No source files were changed; this report is the only file written.

**Method.** Every finding below was read in the source, not inferred from docs. Line numbers refer to the files as they are today. Confidence is marked on each item:

- **Confirmed** — the code path is read end to end and the behaviour follows from it.
- **Likely** — the code supports it but it depends on production data or configuration I could not see.
- **Needs checking** — plausible from the code, but one fact must be verified in prod (Supabase dashboard, Twilio console, Vercel env) before acting.

**What was not done.** No queries were run against production, no tests were run (memory notes say the vitest suite leaks `.env.local` into workers and hits prod), and no build was run.

**Weighting.** Every recommendation is weighed against: one paying client live, a solo founder at 5–10 hrs/week, target of ~10 clients at ~$200/month, solo tradies first. The production usage census in commit `791c1be` (03-09-2026) is treated as ground truth: **0 invoices, 0 quotes chased, 0 price-list items, 191 lead-ack SMS sent, 93 missed-call leads.** That census says the client uses this as a *lead intake and SMS* tool, not as a quoting/invoicing tool. Recommendations follow the usage, not the feature list.

## 1. Critical issues — tenant isolation, data integrity, billing

These override the priority order. Ordered by blast radius for the live client, then for client #2.

### C1. One Twilio sender number for every tenant — inbound replies route to whoever owns that number

**Confidence: Confirmed in code; the prod routing table is Needs checking.**

Every customer-facing SMS (lead acknowledgement, quote link, booking confirmation, booking reminder, review request, on-the-way) is sent from a single global `TWILIO_FROM_NUMBER`:

- [api/_lib/sendBrandedSms.ts:32](../api/_lib/sendBrandedSms.ts:32) and `:76` — `From: from` is the env var, no per-org lookup.
- [api/send-sms.ts:1069](../api/send-sms.ts:1069) — same for the ETA/review modes.
- [api/_lib/sendEmployeeAlert.ts:35](../api/_lib/sendEmployeeAlert.ts:35) — same for staff alerts.

Inbound routing, by contrast, is per-org by the *called* number: [api/_lib/resolveOrgFromDid.ts:24-40](../api/_lib/resolveOrgFromDid.ts:24) looks up `org_phone_numbers.phone_number` and drops the message into `unrouted_inbound` when there is no mapping.

Consequence the moment a second org is live: org B's customer receives an ack SMS from the shared number, replies to it, and the reply arrives at the number's `org_phone_numbers` owner (org A). The customer's name, phone and message land on org A's board as a fresh "SMS Enquiry" lead ([api/inbound-sms.ts:185-197](../api/inbound-sms.ts:185)), and org A's ack SMS fires back at org B's customer. That is a tenant data leak plus a customer-facing brand mix-up. Today with one org it is harmless, which is why it has not surfaced.

Same shape, other channels: `META_PAGE_ACCESS_TOKEN` env fallback in [api/_lib/messengerBot.ts:32](../api/_lib/messengerBot.ts:32), `VOICEMAIL_MAILBOX_ORG_ID` single org in [.env.example](../.env.example), `CAMPAIGN_ORG_SLUG` defaulting to `'default'` in [api/_lib/handleCampaignQuote.ts:18](../api/_lib/handleCampaignQuote.ts:18).

**Fix shape (S):** add `sms_from_number` to `org_phone_numbers` (or a `sms_sender` column on `orgs`), resolve it in `sendBrandedSms` / the two other senders, and refuse to send when an org has no number rather than falling back to the global one. This is the prerequisite for two-way SMS (section 2).

### C2. Invoice email attaches any PDF in the invoice-template bucket, including another org's

**Confidence: Confirmed.**

`handleInvoiceSendEmail` accepts a client-supplied `pdfStoragePath` ([api/send-sms.ts:543](../api/send-sms.ts:543), passed through at `:589`) and `collectPdfAttachments` downloads it with the **service-role** client ([api/_lib/invoices.ts:87](../api/_lib/invoices.ts:87), `:96`), which bypasses storage RLS. The storage policy that scopes the bucket to `(storage.foldername(name))[1] = current_user_org_id()` ([supabase/migrations/20250704120100_invoice_storage.sql:14-30](../supabase/migrations/20250704120100_invoice_storage.sql:14)) only protects direct client access. There is no check that the path starts with `auth.orgId + '/'`.

A manager in org A who knows (or guesses; paths are `${orgId}/job-invoices/…` per [src/components/InvoiceStep.tsx:98](../src/components/InvoiceStep.tsx:98)) org B's template path can have org B's letterhead and bank details emailed to an address of their choosing. Invoice template PDFs are exactly the document that carries bank account details.

**Fix (XS):** in `handleInvoiceSendEmail`, reject unless `pdfStoragePath.startsWith(`${auth.orgId}/`)`. Same guard belongs in `collectPdfAttachments` as defence in depth.

### C3. Offline contact-attempt replay overwrites newer lead state and never reports failure

**Confidence: Confirmed.**

[src/lib/flushOfflineQueue.ts:37](../src/lib/flushOfflineQueue.ts:37) and `:54` run `update(...).eq('id', leadId)` with no status guard and **discard the error** (the result is not destructured). `flushOne` then removes the item from the queue unconditionally ([src/lib/flushOfflineQueue.ts:165](../src/lib/flushOfflineQueue.ts:165)).

Two real sequences on a field phone:

1. Tech logs a call offline → lead is booked by the manager from the office → tech's phone reconnects → lead regresses from `booked` to `contact_attempted` (with `assigned_to` overwritten by pool-pickup fields if it was in the pool). Calendar event still exists; the board disagrees.
2. RLS rejects the update (lead was soft-deleted, or reassigned so the employee no longer matches) → nothing is written, the queue item is dropped, the tech believes the call was logged. The contact round never advances, so the follow-up cron nags forever.

The completion path already does this correctly: [src/lib/flushOfflineQueue.ts:106-131](../src/lib/flushOfflineQueue.ts:106) re-reads status, skips if terminal, and throws on error.

**Fix (S):** mirror the completion guard: add `.eq('status', item.leadStatus)` (or a terminal-status skip), destructure `error` and throw so the item is kept and surfaced.

### C4. Pool pick-up races on the drag, status-menu and call paths — last writer wins silently

**Confidence: Confirmed.**

The manager assign modal does this right: [src/components/AssignLeadModal.tsx:129-152](../src/components/AssignLeadModal.tsx:129) updates with `.eq('status', 'unassigned')`, requests `count: 'exact'`, and tells the user "just assigned by another manager" when zero rows change.

The three employee pick-up paths do not:

- Kanban drag: [src/pages/LeadsPage.tsx:497](../src/pages/LeadsPage.tsx:497) — `update(...).eq('id', leadId)` only.
- Generic lead write used by call/SMS actions: [src/lib/offlineWrites.ts:40](../src/lib/offlineWrites.ts:40).
- Offline replay: covered in C3.

In team mode two technicians who both tap "Call" on the same pool lead within a few seconds both get `assigned_to = me`; the second write wins, the first tech's optimistic UI still shows the lead as theirs until the realtime refetch, and two people phone the customer. `lead_events` will show two `assigned` rows, so it is auditable after the fact, but not prevented.

**Fix (S):** route all status transitions from `unassigned` through one helper that adds `.eq('status', 'unassigned')` and checks the affected count, reusing the modal's pattern.

### C5. A Stripe subscription event would silently downgrade the live client's tier and 403 the money path

**Confidence: Likely (latent).**

Quotes, invoices and card payments are gated at `min_tier: 'pro'` ([shared/featureSwitchCatalog.ts:93-113](../shared/featureSwitchCatalog.ts:93)). The only place tier is set today is at org creation in Platform Admin ([src/pages/PlatformAdminPage.tsx:259](../src/pages/PlatformAdminPage.tsx:259)) or by hand in the table editor. Memory and CONTEXT_BRIEF both say there is no Stripe subscription for the client.

`syncOrgFromSubscription` ([api/stripe.ts:59-98](../api/stripe.ts:59)) unconditionally writes `subscription_tier` from the Stripe subscription on `checkout.session.completed`, `customer.subscription.updated` and `.deleted`, collapsing to `'basic'` on anything not active/trialing. There is no "manual override" flag. The day the client (or you, testing) creates a subscription and it lapses, cancels, or is created on the basic price, every quote/invoice endpoint returns 403 "disabled for this franchise" ([api/send-sms.ts:275-278](../api/send-sms.ts:275), `:530-533`) and `handleInvoicePay` redirects the customer's Pay Now click back to the invoice page with no explanation ([api/stripe.ts:323-334](../api/stripe.ts:323)).

Also: `subscription.current_period_end` ([api/stripe.ts:90](../api/stripe.ts:90)) is fine on the pinned `stripe@17` API version but moves to subscription items in API 2025-03-31+. Pin the API version explicitly in `getStripe()` before ever upgrading the SDK.

**Fix (S):** add `orgs.tier_override` (nullable) that `syncOrgFromSubscription` never touches and `auth.ts` prefers when set. Or, simpler for the next 12 months: drop tier gating entirely and rely on switches (see section 3, "tier system").

### C6. Employees cannot send invoices — the role check names a role that does not exist

**Confidence: Confirmed.**

[api/send-sms.ts:526](../api/send-sms.ts:526): `['manager', 'platform_admin', 'technician'].includes(auth.role)`. The only roles are `manager | employee | platform_admin` ([src/lib/roles.ts:1](../src/lib/roles.ts:1)). The completion checklist renders `InvoiceStep` for every role ([src/components/CompletionChecklist.tsx:216](../src/components/CompletionChecklist.tsx:216)), so a technician who finishes a job, types the amount and taps Send gets "Only team members can send invoices" after uploading a PDF. This is consistent with "0 invoices exist" in the census: the people who close jobs cannot invoice from the app.

**Fix (XS):** replace `'technician'` with `'employee'`. Decide whether the `invoices_manager_write_org` RLS policy ([supabase/migrations/20250704120000_invoices.sql:72](../supabase/migrations/20250704120000_invoices.sql:72)) should also admit employees for read-your-own; the server path uses service role so it is not blocking.

### C7. "Reply STOP to opt out" is promised but a STOP reply creates a lead and sends another ack

**Confidence: Confirmed in code; Twilio-side default opt-out handling for AU long codes is Needs checking.**

The ack SMS copy ends with "Reply STOP to opt out" ([shared/leadAckCopy.ts:8](../shared/leadAckCopy.ts:8)); the booking reminder says the same ([api/_lib/bookingReminder.ts:184](../api/_lib/bookingReminder.ts:184)). Nothing in the app recognises STOP: [api/inbound-sms.ts:146-236](../api/inbound-sms.ts:146) treats every non-empty body as an enquiry, inserts a lead, runs Claude on it, notifies managers, and sends the ack SMS again via `sendLeadAckSmsIfEnabled`. There is no suppression list consulted by `sendBrandedSms`.

If Twilio's carrier-level STOP handling is active on the number, Twilio blocks the *next* send but still delivers the STOP webhook, so the lead and manager alert still happen. If it is not active for the AU number, the customer gets an ack in reply to their STOP, which is a Spam Act 2003 problem and a one-star-review problem.

**Fix (S):** in `finishInboundSms`, match `^(stop|unsubscribe|opt ?out|cancel|quit|end)$`, write to a new `sms_opt_outs (org_id, phone)` table, and return before lead creation; have `sendBrandedSms` check it. Do the same for `START`.

### C8. The solo-tradie preset writes switches at brand scope — provisioning client #2 reconfigures client #1

**Confidence: Confirmed (already known in CONTEXT_BRIEF §6, restated because it is the tenant-isolation blocker for sales).**

[api/_lib/soloTradiePreset.ts:36-55](../api/_lib/soloTradiePreset.ts:36) upserts 15 keys into `brand_feature_switches`. `isFeatureEnabledForOrg` ([api/_lib/featureSwitches.ts:47-56](../api/_lib/featureSwitches.ts:47)) only reads brand-level rows. `org_feature_switch_overrides` was created in [20250701110000_feature_kill_switches.sql:94](../supabase/migrations/20250701110000_feature_kill_switches.sql:94) but no code reads it (grep finds only the migration). Fourteen of the 15 preset keys send SMS/email to *customers of every org on the brand*.

**Fix (M):** read `org_feature_switch_overrides` in `isFeatureEnabledForOrg` and `OrgContext.refreshFeatureSwitches` (org → brand → catalog → code default), and point the preset at the org row. See sprint 2.

## 3. Performance and architecture

### Will hurt the live client within months

**P1. The leads board loads every non-deleted lead the org has ever had, with no limit.** Confirmed.
[src/pages/LeadsPage.tsx:263-275](../src/pages/LeadsPage.tsx:263) selects `*` plus the assignee join, filtered only by org and `deleted_at is null`; completed and lost leads are included. PostgREST caps unbounded selects at 1000 rows (the follow-up cron already documents this at [api/_lib/runContactFollowUpCron.ts:29-34](../api/_lib/runContactFollowUpCron.ts:29)). At 93 missed-call leads in a few weeks plus SMS/email/Messenger, the client will cross 1000 within the year and the *oldest* leads silently vanish from the board, including any still open. Then three follow-up queries do `.in('lead_id', leadIds)` with every id ([src/pages/LeadsPage.tsx:314](../src/pages/LeadsPage.tsx:314), `:337`, `:361`) — as a GET query string, ~37 bytes per UUID. Somewhere between 300 and 500 leads the URL exceeds gateway limits, the query errors, and the catch blocks ([src/pages/LeadsPage.tsx:321-323](../src/pages/LeadsPage.tsx:321)) swallow it: quote/invoice/SMS badges just stop appearing. **Likely** on timing, Confirmed on mechanism.
Fix: filter to active statuses for the board (`status not in ('completed','lost','booking_cancelled')` plus completed-in-last-30-days), add `.limit()`, and move the badge lookups server-side or to a view keyed by `org_id` instead of id lists.

**P2. Missing indexes on the hottest joins.** Confirmed from the migration set (prod may differ — Needs checking via `pg_indexes`).
- `lead_events(lead_id)` — no index anywhere; FK columns are not auto-indexed in Postgres. Hit by every card expand ([src/components/LeadCard.tsx:169-182](../src/components/LeadCard.tsx:169)), the LeadsPage badge query, the activity feed and reports. Only `lead_events_org_created_at_idx` and `lead_events_actor_id_idx` exist.
- `leads(org_id, phone)` — hit by `phoneBelongsToOrg` ([api/send-sms.ts:57-83](../api/send-sms.ts:57)), `findRecentLeadByPhone`, customer linking. Only `leads(org_id)` and `(org_id, email_hash)` exist.
- `events(org_id, start_time)` — calendar range fetch ([src/components/Calendar.tsx:379-383](../src/components/Calendar.tsx:379)) and the booking reminder sweep ([api/_lib/bookingReminder.ts:86-92](../api/_lib/bookingReminder.ts:86)). Only `events_booking_group_id_idx` exists.
- `lead_photos(lead_id)`, `lead_voicemails(lead_id)` — not listed in any migration.
All small tables today; all cheap to add now with `CREATE INDEX CONCURRENTLY`.

**P3. Four unfiltered realtime subscriptions on `leads` each trigger a full refetch.** Confirmed.
[src/pages/LeadsPage.tsx:984-987](../src/pages/LeadsPage.tsx:984), [src/pages/ManagerDashboard.tsx:120](../src/pages/ManagerDashboard.tsx:120), [src/pages/EmployeeDashboard.tsx:79](../src/pages/EmployeeDashboard.tsx:79), [src/hooks/useTeamWorkload.ts:76](../src/hooks/useTeamWorkload.ts:76) subscribe to `postgres_changes` on the whole `leads` table with no `filter:`; RLS stops other orgs' rows reaching the client, but Supabase evaluates the policy per subscriber per change, and every change re-runs P1's four queries on every open device. `useLeadsPoolCount` ([src/hooks/useLeadsPoolCount.ts:25-30](../src/hooks/useLeadsPoolCount.ts:25)) shows the right pattern (`filter: org_id=eq.…`). Separately, no migration adds `leads` to the `supabase_realtime` publication (only `support_messages`/`platform_announcements` in [20260708120000_internal_messaging.sql:106-117](../supabase/migrations/20260708120000_internal_messaging.sql:106)); if prod was enabled by hand in the dashboard that is fine, if not these subscriptions are silent no-ops. **Needs checking.**

**P4. `isFeatureEnabledForOrg` is 3 round-trips and is called 6–8 times per inbound lead.** Confirmed.
[api/_lib/featureSwitches.ts:27-56](../api/_lib/featureSwitches.ts:27): orgs + catalog in parallel, then brand switch. Per inbound SMS it is called for `inbound_sms`, `inbound_auto_assign`, `assignment_exclusions`, `customer_linking`, `manager_new_lead_alerts`, `lead_ack_sms`, `native_web_push` — ~20 queries of pure switch lookup before any work. The brand `sms_templates` row is fetched three separate ways in the same request ([api/_lib/sendBrandedSms.ts:56](../api/_lib/sendBrandedSms.ts:56), [api/_lib/notifyManagersNewLead.ts:55](../api/_lib/notifyManagersNewLead.ts:55), [api/_lib/processInboundLead.ts:280](../api/_lib/processInboundLead.ts:280)). Not a scaling wall at 10 tenants, but it is why an inbound SMS pipeline "routinely runs longer than 15 s" (comment at [api/inbound-sms.ts:91-94](../api/inbound-sms.ts:91)). Fix: one `loadOrgRuntimeContext(orgId)` that returns org + brand + all switch values, passed down the pipeline.

**P5. Every team-mode inbound lead geocodes synchronously against Google before insert.** Confirmed.
[api/_lib/teamInboundLead.ts:137](../api/_lib/teamInboundLead.ts:137) inside `insertRawFirstLead`, i.e. *before* the raw-first insert that is supposed to guarantee the lead is saved. A Google timeout delays the save; a Nominatim fallback ([api/_lib/staticMap.ts](../api/_lib/staticMap.ts)) rate-limits at 1 req/s. Move geocoding after the insert (it only feeds the proximity tiebreak).

**P6. Live-month reports load a month of `lead_events` unbounded.** Likely.
[src/lib/reporting/fetchReportData.ts:188-199](../src/lib/reporting/fetchReportData.ts:188) — ~6–10 events per lead × 100+ leads/month lands on the 1000-row cap and silently under-counts. Add pagination via `.range()` or aggregate in SQL (the monthly snapshot RPCs already exist for closed months).

### Bundle and service worker

**P7. Every install precaches the 3D visualiser.** Confirmed.

## 5. Bugs and security findings

Ordered by impact. C1–C8 above are not repeated.

**B1. HTML injection into customer emails from lead data.** Confirmed, low-medium.
`interpolateTemplate` ([api/_lib/smsTemplates.ts:3-11](../api/_lib/smsTemplates.ts:3)) does no escaping, and the default quote/invoice templates place `{{customerName}}` and `{{org.name}}` straight into HTML ([api/_lib/emailTemplates.ts:41-51](../api/_lib/emailTemplates.ts:41), `:104-118`). `customerName` originates from an inbound SMS/email/Messenger name field. `senderBlock` in quotes is also unescaped ([api/_lib/quotes.ts:196](../api/_lib/quotes.ts:196)) while the invoice equivalent is escaped. Booking confirmation escapes correctly ([api/_lib/bookingConfirm.ts:132-137](../api/_lib/bookingConfirm.ts:132)). Fix: escape every scalar var before interpolation in the email builders (HTML-typed vars like `lineItemsHtml`, `payButton` stay raw).

**B2. RPC functions callable by any client role.** Confirmed.
`increment_rate_limit` ([20260806150000_rate_limits.sql:21](../supabase/migrations/20260806150000_rate_limits.sql:21)) and `increment_ai_usage` ([20260806160000_ai_usage_monthly.sql:14](../supabase/migrations/20260806160000_ai_usage_monthly.sql:14)) have no `REVOKE … FROM anon, authenticated`. PostgREST exposes public functions by default, so any visitor can call `increment_rate_limit('public-quote-public-get:<victim ip>', …)` to lock a customer out of their quote page for a minute, or inflate an org's AI counter to its ceiling. Contrast with `expire_overdue_leads`, which does revoke. Fix: `REVOKE EXECUTE … FROM PUBLIC, anon, authenticated; GRANT … TO service_role;` for both (prod via Management API).

**B3. PostgREST filter built from user input.** Confirmed, low.
[src/components/EventModal.tsx:484](../src/components/EventModal.tsx:484) interpolates the lead search string into `.or(\`name.ilike.%${leadSearch}%,…\`)`. A comma or parenthesis in the search breaks the query (RLS still bounds rows to the org, so no leak). Use `.ilike()` chained with `.or()` on sanitised input, or strip `,()` first.

**B4. Quote accept can double-fire.** Confirmed, low.
[api/_lib/quotes.ts:467-473](../api/_lib/quotes.ts:467) updates with `.eq('status','sent')` but does not check affected rows before upserting the signature and notifying every manager; two simultaneous accepts (double-tap on a slow connection) produce two "Quote accepted" notifications and the second signature overwrites the first via `onConflict: 'quote_id'`. Add `.select('id')` and bail on zero rows, as the assign modal does.

**B5. Inbound email trusts an attachment URL and has no dedupe.** Confirmed.
[api/inbound-email.ts:132](../api/inbound-email.ts:132) `fetch(voicemailAttachment.url)` — bounded by `INBOUND_SECRET` basic auth so only CloudMailin can reach it; acceptable, but restrict to CloudMailin's storage host. The dedupe gap is feature #5.

**B6. Any org member can SMS any teammate arbitrary text through `?action=notify`.** Confirmed, low.
[api/send-sms.ts:129-172](../api/send-sms.ts:129) accepts free-form `title`/`message` and `type`; for any `type` other than `lead_assigned`/`contact_follow_up`, `notifyOrgUser` sends it by WhatsApp/SMS ([api/_lib/notifyUser.ts:109-113](../api/_lib/notifyUser.ts:109)). Rate-limited to 20/min per user. Restrict `type` to an allow-list and `message` length.

**B7. A sole manager can delete their own account and orphan the org.** Confirmed, low.
`deleteOwnAccount` ([api/_lib/accountDeletion.ts:24-70](../api/_lib/accountDeletion.ts:24)) has no "last manager" check. Leads survive (FKs are SET NULL) but nobody can log in to see them until a platform admin intervenes. Add a guard: refuse when the caller is the only non-departed manager.

**B8. Request-derived base URL in customer-facing links.** Confirmed, mitigated.
`getRequestBaseUrl` ([api/send-sms.ts:39-54](../api/send-sms.ts:39)) trusts `x-forwarded-host` for the quote acceptance link and the Pay Now link ([api/_lib/invoices.ts:177](../api/_lib/invoices.ts:177)). On Vercel the header is platform-set, so this is safe today; it becomes a phishing vector if the API is ever fronted by anything else. Prefer `getPlatformUrl()` and drop the header path.

**B9. Module-level Supabase client with non-null assertions.** Confirmed, low.
[api/inbound-sms.ts:32-35](../api/inbound-sms.ts:32) and [api/inbound-email.ts:24-27](../api/inbound-email.ts:24) call `createClient(process.env.SUPABASE_URL!, …)` at import. A missing env var throws at cold start and 500s every action on the hub (including `meta-webhook`), instead of the graceful 503 the other hubs return via `getSupabaseAdmin()`.

**B10. Booking-reminder and ack SMS ignore per-customer opt-out; no consent record exists.** See C7. For the Spam Act, also log consent source on the lead (`inbound` = implied consent for a reply; `manual` entry = needs a tick).

**B11. `resend` is dynamically imported inside the quote path but not the invoice path.** Confirmed, cosmetic. [api/_lib/quotes.ts:175](../api/_lib/quotes.ts:175) vs `sendTransactionalEmail`. Harmless, but two code paths to Resend means two sender-fallback chains (S1).

**Verified as not a problem:** Twilio signature verification uses `req.headers.host` ([api/inbound-sms.ts:36-43](../api/inbound-sms.ts:36)), which matches the rewritten URL Twilio signed; Meta webhook HMAC is checked over raw bytes; Stripe webhooks verify signatures with separate secrets; `push-rotate` is scoped to the existing row's `user_id`; `analytics-track` forces `orgId` from the session; `create-user` blocks cross-org invites and role escalation.
